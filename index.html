Cases.

마감을 세 번 확인한 이유 GETDDO

상황
마감 직전에는 응모가 한꺼번에 몰립니다. “아직 열려 있음”을 확인한 뒤 저장하는 사이에 마감이 지날 수 있습니다.
원인
확인과 저장이 한 단계가 아니어서, 확인한 순간의 상태가 저장할 때까지 그대로라는 보장이 없습니다.
조치
이벤트 행을 잠근 직후, 응모권 차감 직후, 커밋 직전에 마감을 확인합니다. 커밋 직전 확인에서 마감을 넘었으면 응모 전체를 롤백합니다.
결과
스테이징 API 2대에서 200명이 마감 10초 전부터 5초 뒤까지 응모를 보내는 테스트를 3회 했습니다. 접수, 차감, 사용 이력이 모두 1,522건으로 같았고, 마감 뒤 확정은 0건이었습니다.측정됨
남은 과제
마지막 확인과 DB 커밋 사이의 짧은 틈은 구현으로 없앨 수 없어서, 공용 명세에 예외로 승인받았습니다.

정합성 규칙을 통과했는데도 결함이 있었던 이유 GETDDO

상황
같은 사용자가 퀴즈를 문항별로 동시에 제출하면 100명 중 23명이 정답 기록만 남고 보상을 받지 못했습니다. 중복 지급은 없었습니다.
원인
미리 정한 정합성 규칙 8개에 “전 문항 정답이면 완료와 청구가 있다”는 검사가 없었습니다. 규칙이 통과해도 결함이 없다는 뜻은 아니었습니다.
조치
같은 사용자의 제출이 겹치지 않게 순서대로 처리하도록 고쳤습니다.
결과
같은 부하(300명)로 다시 테스트해 보상 누락과 중복이 0이었습니다.측정됨
남은 과제
수정 뒤 연결 풀(서버당 10개)이 차서 503이 1차 264건, 2차 61건 났습니다. 같은 제출 ID로 재시도하면 최종 실패는 0이었지만, 수정이 풀 압력을 키웠는지는 아직 가르지 못했습니다.
내 역할
테스트를 해 보기로 하고, 직접 실행해 DB를 대조하다가 결함이 드러났습니다. 원인 분석과 수정 코드는 AI가 작성했습니다.

재고 판단을 Redis가 아니라 DB에 맡긴 이유 Mealiver-IT · 팀 결정

상황
V2 비관적 락은 초과 발급이 없었지만, 재고 한 행에 요청이 몰려 재고 1만 개 중 9,766건과 9,891건만 발급됐습니다.
원인
다음 단계로 Redis 이중카운터를 계획했지만, 실패한 요청도 앞 카운터를 소모해 재고가 남았는데 품절될 수 있었습니다. 멘토링에서는 Redis를 원장으로 두면 장애 때 기준으로 삼을 데이터가 없어진다는 조언을 받았습니다.
조치
판단은 끝까지 DB가 하고, Redis는 품절 뒤 요청만 거르는 사전 필터로 바꿨습니다(V3). 남은 경합은 재고를 50개 행으로 나눠 분산했습니다(V4).
결과
같은 조건 테스트 6회 모두 초과 발급 0건이었고, V4는 두 번 모두 정확히 1만 건이 발급됐습니다. 이와 별도로 V4 도입 뒤 한 테스트에서 261건 초과가 재현됐는데, 원인은 재고 판단이 아니라 실제로는 커밋된 INSERT를 실패로 보고 재고를 되돌린 복원 로직이었습니다. 복원 전에 커밋 여부부터 확인하도록 고쳤습니다.측정됨 · 팀 테스트
남은 과제
V1(제어 없음)은 그림으로만 설명해서, 초과 발급을 직접 재현한 대조군 데이터가 없습니다.
내 역할
논의에 참여하고, 결정과 이유를 AI와 함께 문서로 정리했습니다. 테스트에 쓸 더미 데이터를 만들었습니다.

대기열이 있는데도 좌석 선점이 느렸던 이유 MINGPARK

상황
대기열이 동작하는데도 좌석 선점 API의 평균 응답이 200ms대까지 올랐습니다.
원인
로그인만 하면 대기열을 거치지 않고 선점을 요청할 수 있어, 요청이 그대로 Redis 락 경합으로 이어졌습니다. AI 코드 점검에서 지적된 경로를 확인한 것입니다.
조치
좌석 선점 API에 대기열 통과 검사를 추가했습니다.
결과
같은 조건(300 VU / 30초 / 50석)에서 코드만 바꿔 두 번 돌렸습니다. 평균 응답이 한 자릿수 ms로 줄었고 50석이 모두 예매됐습니다. 대신 사용자는 평균 약 8초를 대기열에서 기다립니다.측정됨 · 로컬
남은 과제
로컬 PC 한 대에서 서버, MySQL, Redis, k6를 함께 돌린 결과라 절대값이 아닌 전후 비교입니다.

이 페이지의 수치는 저장소 기록과 최종 발표 자료에서 확인한 값만 적었습니다. 측정됨은 실행 기록이 남아 있는 결과, 시나리오는 동작만 확인한 결과입니다.
