프로젝트 — 대표 사례: GETDDO

LG유플러스 유레카 과정에서 콘서트 예매 대기열, 인증, 쿠폰 시더, 응모권 정합성을 맡았습니다. 동시에 들어오는 요청을 처리하는 자리도 있었고, 데이터를 쌓고 맞추는 자리도 있었습니다. 그중 담당 범위가 가장 컸던 이벤트 응모 서비스(GETDDO)를 먼저 적습니다.

측정됨 스테이징 서버 2대에서 200명이 마감 경계(마감 10초 전부터 5초 뒤)에 몰리는 상황을 3회 시험했고, 마감 뒤 확정은 0건이었습니다. 시험을 실행하는 과정에서 퀴즈 보상 누락 결함이 드러났고, 수정 뒤에도 연결 풀 부족으로 503이 남아 “5xx 0” 기준은 달성하지 못했습니다.

지켜야 했던 것

  1. 같은 요청은 한 번만 접수합니다. 접수란 응모가 확정되는 것입니다.
  2. 마감 뒤에는 확정되는 응모가 0건이어야 합니다.
  3. 서버가 두 대여도 결과는 하나여야 합니다.

어떻게 지켰나

클라이언트가 보낸 멱등 키로 중복을 걸러내고, 행 잠금과 DB 유일 제약으로 동시 요청이 같은 자원을 두 번 쓰지 못하게 했습니다. 마감 경계는 세 번 확인합니다. 이벤트 행을 잠근 직후, 응모권 차감 직후, 커밋 직전입니다. 마지막 확인과 커밋 사이에 시각이 지날 수 있는 짧은 틈은 구현으로 없앨 수 없어서, 공용 명세에 예외로 승인받았습니다.

어떻게 확인했나 측정됨

깨지면 안 되는 규칙 8개를 AI와 함께 정하고 SQL 전수 검사로 돌렸습니다. 시험과 스크립트는 AI가 만들었고, 시험해 보기로 한 판단, 스테이징 API 2대에서의 실행, DB 대조는 직접 했습니다.

  • 마감 경계 시험: 200명, 마감 10초 전~5초 뒤, 3회, 총 3,019건(접수 1,522 + 마감 거절 1,478 + 응모권 부족 19).
  • 같은 사용자의 동시 요청 시험: 100명(3장 보유 60명, 1장 보유 30명, 같은 키 10명)이 500건을 보냈고, 접수 220 = 차감 220 = 사용 이력 220이었습니다.

시험이 드러낸 결함 측정됨

증상
같은 사용자가 퀴즈를 문항별로 동시에 제출하면 100명 중 23명이 정답 기록만 남고 보상을 받지 못했습니다. 중복 지급은 없었습니다.
빠진 규칙
규칙 8개로는 이 결함을 잡지 못했습니다. “전 문항 정답이면 완료와 청구가 있다”는 검사가 규칙에 없었기 때문입니다.
수정
PR #184(10/26 병합). 수정 뒤 같은 부하(300명)에서 보상 누락과 중복이 0이었습니다.
남은 503
수정 뒤 연결 풀(서버당 10개)이 차서 503이 1차 264건, 2차 61건 발생했습니다. 같은 제출 ID로 재시도한 시험에서는 최종 실패 0, 퀴즈 100명 전원이 보상 1건이었습니다. 수정이 풀 압력을 키웠는지는 이 시험에서 가르지 못했습니다.
내 역할
결함은 정합성 시험을 직접 실행해 DB를 대조하는 과정에서 드러났습니다. 원인 분석과 수정 코드는 AI가 작성했습니다.

보호 장치를 하나씩 빼 보기 측정됨

보호 장치 7종을 하나씩 제거한 뒤 같은 시험을 돌렸고, 6종에서 규칙 위반이 재현됐습니다. 로컬 환경에서 실행한 시험이라 스테이징 실측과는 조건이 다릅니다. 위협 지점은 AI와 함께 정했습니다.

남은 한계

  • 위협 12개 가운데 서버에서 확인하지 못한 3개(월말 만료, 처리 도중 실패, 롤링 배포)가 남아 있습니다. 이 시험을 이어서 진행하려 합니다.
  • 연결 풀 503의 원인을 특정하지 못했습니다. 풀 크기와 수정 전후를 나눠 비교해 원인을 가르고 싶습니다.
  • 시험이 드러낸 규칙 누락처럼, 완료 조건을 규칙에 하나씩 추가하며 전수 검사 범위를 넓혀 가려 합니다.

TOCKTALKS — 실시간 모의투자 시나리오

2026.07 (2주) · 5인 · Java 21, Spring Boot 4.1, JWT, Redis, MySQL, WebSocket/STOMP

Refresh 토큰을 1회용으로 회전시키고, 이미 회전된 토큰이 다시 들어오면 해당 계정의 토큰을 선제 무효화하도록 했습니다.

Auth(자체 로그인과 Kakao OAuth2)와 Room을 담당했습니다. Access 토큰은 1시간, Refresh 토큰은 14일(Redis 저장)로 나누고, 로그인 5회 실패 시 5분 잠금을 Redis 카운터로 구현했습니다. 로그아웃 뒤 Access 토큰이 남는 문제와 Refresh 재사용 탐지 누락은 AI 점검에서 지적된 것을 코드로 확인하고 반영했습니다. Redis 장애 때는 fail-open으로 로그인이 막히지 않게 했습니다.

한계: CI/CD가 없고 성능 측정도 하지 않았습니다. 부하 측정과 CI 구성을 우선 진행하려 합니다. fail-open은 가용성을 택한 대신 장애 중 로그인 대입 방어가 열립니다. 서비스 성격에 맞춰 fail-closed와 비교한 뒤 다시 판단하고 싶습니다.

Mealiver-IT — 배달앱 선착순 쿠폰 측정됨

한계: 시더 단계별 소요 시간을 기록하지 않아 배치 옵션의 효과를 수치로 비교할 수 없습니다. 다음에는 단계별 소요 시간부터 기록해 옵션 간 차이를 확인하려 합니다.
